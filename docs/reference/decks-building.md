# Decks — building, checking and sharing

**Read when:** building a deck with `npm run deck`, checking or reviewing one, filing it under a category, sharing it between Harry and Claude, or touching the timer, zoom, tablet fit or the saved writing. (Part of the decks reference; the model, pages and storage are in `decks.md`.)

## Building a deck quickly (`builder.ts`, `deckChecks.ts`, `npm run deck`)

A new deck is a short script, kept outside the repo (the scratchpad), that default-exports a function returning the deck. `S` makes slides (title, board, deliberate practice, general practice generator, book activity, quick grid, Depth card, discussion…) and `Q` makes questions with the tool's own working (`Q.rounding`, `Q.estimate`, `Q.fraction`, `Q.open`); each `Q` builder writes the working the tool does, so only the numbers are typed.

```ts
import { Q, S } from "/src/decks/builder";
export default () => ({ id: "my-deck", title: "My deck", summary: "…", tool: "estimation", slides: [
  S.title("m-title", "My deck", "Round first"),
  S.deliberate("m-set", "Estimate products", [["42", "18"], ["63", "29"]].map(([a, b], i) => Q.estimate(`m-${i + 1}`, "level1", a, "\\times", b)), "Brief."),
  S.general("m-gen", "Whiteboards", "estimation", { sub: "estimation", level: "level1" }, 3),
] });
```

Fixed questions that carry a tool's own working: `Q.ratioSimplify(id, level, parts, ask?, method?)` and `Q.ratioFraction(id, level, spec)` make a question with the Ratio Manipulation generator's code (fixed numbers, wording chosen with `variant`) and check its answer from the parts; `fromWorked` (`questions.ts`) turns any generated question into a fixed one. A working step that is a picture (a ratio table growing a row per step, the fraction bar model) is kept as a line `caption` + newline + `@ratiotable {json}` or `@bar {json}` in the question's `explanation`, and the player draws it (`WorkedPicture.tsx`); edit it as text in the question editor.

`npm run deck -- build <script>` builds the deck, runs the checks and writes `src/decks/data/<id>.json` (it refuses to overwrite an existing deck without `--replace`, since that file may hold edits made in the player: pull first). `npm run deck -- check <id|all> [--layout]` runs the content checks (maths renders, answers where the working ends, sets of at least 5, Depth cards ask new numbers, generators run at their level and do not pile on one answer, text fits its box) and with `--layout` also starts the app and measures every slide. The same checks run in the tests for every built deck (`deckBuilder.test.ts`). House rules for what to build: `docs/design/LESSON_STYLE.md`. <!-- ref -->

### Decks in folders (`api/_folders.ts`, `src/decks/folders.ts`, `components/FolderView.tsx`, `FileUnder.tsx`)

Plan and later steps: `docs/pathways/deck-folders.md`.

- **One way to file and find decks, for both views** (decided with Harry, 2026-11-24): the Decks page is a file explorer over a tree of folders. Signed in it opens on **By class** and also has **By topic** (the strands and topics, now folders too), remembered on the device (`mt-decks-view`). Signed out there are no tabs: only the topic tree's **published** decks, read-only (`FolderView` with `publicMode`; the class tree is signed-in only). The screen is a breadcrumb trail (Classes › Year 9 › 9M6, or Topics › A-Level › Further Maths), the opened folder's subfolders as tiles (name, decks inside it and its subfolders, counted once each), and its decks as the usual preview cards, **most recently made first from the left**. `?folder=<id>` in the address keeps the place; an unknown or deleted folder shows the top level. A deck in no folder of the tree is under the virtual **Not filed** tile at the top level (`UNFILED`), so no deck is unreachable; new decks start there unless they carry a strand.
- **The two trees.** `class`: seeded once from `DEFAULT_CLASS_TREE`, a folder per year (Year 7, 8, 9, 10, 11, A-Level) holding the classes (7M1; 9M6, 9M3, 9M2; 12FM, 13MA, 13FM). `topic`: the strands and topics. A database that already had categories has them **copied once** into the topic tree on first read (same ids, order and filing; decks that carry a `strand` and were not filed anywhere are filed under it, Decision Mathematics into A-Level › Further Maths); the old `deck_categories` and `deck_filing` tables are left in place and no longer read. A new database gets `DEFAULT_TOPIC_TREE`. A marker row in `deck_meta` per tree stops it seeding again, so a folder deleted later stays deleted. A brand-new deck is filed under the strand it carries, once, on its first save (`fileNewDeckByStrand`); later saves leave it where it is.
- **Editing the folders** (`canEdit`: signed in, not on a phone, which only previews): **New folder** (inside the open folder, or at the top level), and on each tile rename (pencil), move earlier or later, **Move into…** (any folder that is not itself, not inside it and not its current parent; **Top level**), and delete. **Drag** a deck card or a folder tile onto a folder tile or a breadcrumb to move it there (a card leaves the open folder; dropped on **Not filed** it leaves every folder of the tree; **Add a deck…** puts a deck in a second folder). A touch screen cannot drag, so the Move into… menu and Add a deck… cover it. The deck editor's **About the deck** has the same filing as two checklists, one per tree (`FileUnder`). Rules, enforced by `applyFolderOp` and tested: names are unique among siblings (case-insensitive) and 1 to 60 characters; no more than `MAX_DEPTH` (6) levels; a folder cannot go inside itself or a folder of another tree. **Deleting a folder deletes no deck:** its decks go into its parent (a top-level folder's decks are simply in no folder) and its subfolders move up one level (renamed "name (from folder)" if the name is already taken there); the screen asks first.
- **Folders are a table, not a list in code.** `maths.deck_folders (id, tree, name, parent, position)` and `maths.deck_folder_items (folder_id, deck_id)`, apart from the decks, so filing a deck makes no deck version and cannot clash with an edit. A deck can be in several folders of a tree; setting a deck's folders replaces its folders in that tree only. A deleted deck leaves its folders.
- **Loaded on open.** The tree (folders, counts, which folders each deck is in, how many decks are in none) is read once; a folder's decks, with their first slides (from the working copy, or the published copy for the public read), are read only when it is opened.
- **"Made" is `maths.decks.created_at`**, set when a deck is first saved; decks that existed before it was added got their earliest saved version's time (an approximation). Editing a deck does not change it.
- **API:** admin: `GET ?folders=<tree>`, `GET ?folder=<id>` (`folder=unfiled&of=<tree>` for Not filed), `POST {folders: {deckId, tree, folderIds}}` (a deck's folders), `POST {folderOp: {op: add | rename | move | reorder | delete, …}}` (the folders themselves; answers with the whole tree). Anyone: `GET ?folders=topic&public=1` (published decks only, only the folders that lead to one, cached a minute) and `?folder=<id>&public=1`. The old `?categories` reads and writes are gone. Tests: `deckFolders.test.ts`.
- **For Claude:** `npm run deck -- categories [--tree class]` prints a tree and the decks in each folder (and Not filed); `categories add "<name>" [--under "<folder path>"]` adds a folder; `file <deck-id> "<folder path>" | none [--add]` files a deck (for example `"A-Level > Further Maths"`). A deck built with `strand: "Number"` is filed there when first pushed; otherwise it starts under Not filed. These need a deployment that has `api/_folders.ts` (`DECKS_URL=<it>/api/decks` until it is on main).

### Looking at a deck, shared pieces and the build rules (`pieces.ts`, `deckRules.ts`, `deckReview.mjs`)

- **The look card:** `npm run deck -- looks <script>` builds a script to a temp file (the repo is untouched; `build <script> --out <file>` does the same) and writes contact sheets of one slide of each kind in every state: each question of a question set, the working open, a book-work grid with its answers shown. Harry approves these before the rest is built.
- **Review:** `npm run deck -- review <id> [--file f] [--kinds]` writes contact sheets of every slide with all its clicks revealed (the first question and its working-open view; `--kinds` gives one slide of each kind with every question). `sheet <id> 3,8,13` is one picture of chosen slides, also with every click revealed.
- **Checks that look at the drawn slide** (`scripts/deckLayoutSmoke.mjs`, run by `check --layout` and `verify`): spills, runs off the slide, overlaps, at rest, on every question, with the working open and with the answers shown; and a warning when a short word or number is left alone on the last line of a text (`DEBUG_LINES=1` prints how each text breaks into lines). The editor's layout warnings (`layoutAudit.ts`) follow the first three; the rest is terminal-only.
- **Shared pieces** (`src/decks/pieces.ts`, exported from `builder.ts`): `S.whiteboard` (full-width, inset, centred; `{ table: true }` for a table under the question), `S.plainBook` (plain big numbers, centred), `S.exitRows` (one question to a row), `S.pairModel` (two numbers as headings with their pairs underneath, common values ringed, footers by click); `titleEls`, `makeSlide`, `textEl`, `lineEl`; `quiet` and `hintLine` (small grey hints), `mathsStack` and `mathsGrid` (one pair to a line, lined up), `green`, `assertCentred`; and the `LOOK` tokens (sizes, colours, the title place). The worked example is `specs/decks/factors-hcf-systematic-listing.build.ts`.
- **Build rules** (`src/decks/deckRules.ts`): `assertFreshNumbers` stops a build when a worked number is asked about, a number is asked about twice inside a section, the exit ticket reuses a number or a pair repeats. The deck check warns about the first for any deck, `npm run deck -- build` turns that warning into a failure (`--allow-repeats` overrides), and a title that sits somewhere other than where its family usually has it is a warning too.
- **Unmerged code:** `push`, `verify` and `review` warn when the branch changes player or shared code that is not on main, because the live site runs main and a deck that relies on it looks different there until it is merged.

### Sharing one deck between Harry and Claude (merging)

Two people can edit one deck. `api/_deckMerge.ts` is a pure three-way merge (base, incoming, current) by slide and by element, then field by field within an element: a change on one side is kept, edits to different things on both sides are both kept, an edit beats a delete, additions on either side are kept (ordered after the item they followed), and when both changed the very same field the winner's value is kept and the clash is reported. The winner is Harry (the editor's saves are `incoming`; Claude's pushes are `by: "Claude"`, so the stored copy wins). The merge is used in three places:
- **The server** (`POST /api/decks {deck, base, by}`): reads the stored deck with its ETag, merges the save into it, writes with the ETag (retrying if another save got in first), and answers `{merged, conflicts, deck}`; a merged deck gets a new `updatedAt`, so every device picks it up. A save with no `base` replaces the deck, as before. Every response carries `x-deck-merge: 1`.
- **The editor** (`store.ts` keeps each deck's base in `mt-deck-base:<id>`: set each time a deck is pulled or a save is accepted; the first copy a page saw is used until then). A save sends it; the server's merged deck is folded into what is on screen (`takeShared`: the undo history gets the same changes, so an undo does not take them away), and the editor looks for other changes only when asked (File → **Check for changes**, `checkForUpdates`: one read of that deck; the deck list (Deck editor page) has a **Check for changes** button for every deck, which calls `syncAllDecks` in `store.ts` (brings each newer deck up to date on the device and names the ones that changed). No polling, so an open editor does not keep the database awake). A save that adds nothing to the base is not sent.
- **`npm run deck`**: `pull` writes `.deck-base/<id>.json` (git-ignored); `push` sends it, takes the merged deck back as the file and prints any clashes, and refuses to run if the service does not send `x-deck-merge` (an older deployment would overwrite the whole deck) or if there is no base (`--replace-whole` is the deliberate overwrite). **The live copy is the master and the repo file is its snapshot:** `check <id|all> --live` checks the live copy directly (and with `--layout` draws that copy, not the repo's; nothing in the repo is read or written); `backup [<id>|all]` writes the live copies into `src/decks/data` (a file with unpushed edits, i.e. one that differs from its `.deck-base`, is left alone and reported); `publish <id>` publishes the live copy (`--file` publishes the repo file) and then backs it up. Commit the snapshots so git keeps the history and the tests have the data; the app only uses them as the first-run fallback.
- **Slide order is not merged: the stored order wins.** Moving a slide in a pushed file is silently undone, and after any merged push the CLI writes the merged deck back over the file (so re-apply a move after a push). To reorder: pull, confirm the shared copy has not moved since (compare it with `.deck-base/<id>.json`), make the move, delete `.deck-base/<id>.json` and push with `--replace-whole` (no base means the file replaces the whole deck), then read the shared copy back to check the order.

Tests: `deckThreeWayMerge.test.ts` (the rules, and the real Manipulating ratios case), `decksSave.test.ts` (the server path against an in-memory Postgres (`src/tests/testDb.ts`, PGlite), either order, retry), `decksStore.test.ts` (list, delete, publish and its cache, questions, two saves at once), `migrateDecks.test.ts` (the Blob import), `deckSync.test.ts` (the base, adoption).

### Fitting the screen on a tablet

The player and the editor are as tall as the screen the person can actually see (`useVisibleHeight`, `src/shared/visibleHeight.ts`, with the `.h-app` class in `index.css`): the page height follows `window.innerHeight`, so a tablet browser's address bar no longer pushes the bottom of the slide, or the player's bar, off-screen, and the slide scales to fit what is visible. (The old `h-screen`, `100vh`, is the page with those bars hidden.)

### Zooming the editor's slide

The slide can be enlarged (to 600%) so a box on it is big enough to write in, or shrunk (to 30%) to see it small; 100% is the whole slide fitted to the window. **Two fingers pinch to zoom in or out and, moving together, pan**; **Ctrl + scroll** (and a trackpad pinch) zooms at the pointer; the **+ / − and % buttons** at the bottom right of the canvas step the zoom, and the % button fits the whole slide again. The slide is drawn at the larger size inside a scrolling area (`stageRef`; `scale = fitScale × zoom`) instead of being magnified as a picture, so lines stay sharp and drawing, dragging and handles use the same coordinates as at 100%. A second finger cancels anything the first had begun. On a touch screen where a stylus has been used, the stylus writes and one finger pans; without a stylus one finger writes. Zoom is a view setting only: it is not saved with the deck and stays when you change slide.

### The timer

A countdown of 1 to 10 whole minutes, drawn as a strip under the slide in the player (the player scales the slide down to make room, so the strip does not cover content) (a line that shrinks, amber in the last quarter and red in the last tenth, with the time, a pause or play button and a close button at the right; at zero it reads Time and the line pulses). Logic in `timerMath.ts` (a countdown is its total, the seconds left when last paused and the clock time it ends at, so the redraw rate does not matter), parts in `Timer.tsx`. **Callable on any slide:** the clock button in the player's top bar (or the full-screen control pill) opens a menu of 1 to 10 minutes and choosing one starts it at once; `T` opens the menu, or pauses and resumes a timer that is already showing. **On a slide:** `Slide.timer = { minutes, auto? }` (Slide settings → Timer in the editor, or `S.starter(id, title, minutes)`): the strip appears with the slide and starts at once unless `auto` is false. A timer belongs to the slide it was started on: moving to another slide clears it. Slide timers are checked by the deck check and the decks API.

### Writing: saved on a slide, and kept while a deck is open

Two separate things. (1) The editor's **Pen** writes into the slide itself (the `ink` element above), so it is saved with the deck and seen by everyone. (2) The player's pen (the app-wide `InkOverlay`) is Harry's live annotation: its strokes now **stay with their slide while the deck is open** (`DeckPage` reads them through `src/shared/inkBridge.ts` when you leave a slide and puts them back when you return, in slide units, so a resize or full screen moves them with the slide) and are gone when the deck is closed. Moving between questions inside a slide still clears the pen, as before.
